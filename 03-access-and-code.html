A0 · Three words that make this page readable

Most of page 3 is tables about access. Three terms carry the rest, and they are ordinary ideas under technical names.

Repository
A folder of code that remembers every change. Seadon has two: seadon.production for the theme, seadon-backer-program for the app. Both live on GitHub, and both can be copied to any laptop with one command. Reading a repository is harmless; pushing to it changes the product.
Deploy
Putting new code live. The app deploys through Vercel: you run one command and the live app updates within a minute. The theme deploys through Shopify: you publish a theme, and the storefront changes at once. A deploy is not a save. A save keeps a change on your machine.
Token
A long secret string that lets a program act on Shopify without a human password. The app holds one so it can read orders and write claims. Tokens live in Vercel's settings, never in code and never in a document. A token that leaks is a password that leaked.

What goes wrong if access is not transferred properly

  • The successor can log in but cannot deploy, because the deploy needs a token or an account they do not hold.
  • The app keeps working until the short-lived token expires, then claims and prices stop with no obvious cause.
  • Nobody can rotate a leaked credential, because only one person holds the account that mints tokens.
  • Shopify blocks bulk operations and the only fix sits behind an account nobody else can open.
  • Six months later the store needs an urgent theme fix, and the only person who knows the publish sequence has left.

A3 · Tests, and the state they are in

verified Both suites were run on 25 November 2026 from a clean checkout on this machine.

The app suite works

cd seadon-backer-program
node --test tests/*.test.js
# tests 288 · pass 288 · fail 0

288 tests, zero dependencies, roughly 200 milliseconds. The handover plan says 283, which was true at an earlier commit; treat 288 as the current count.

The theme suite does not run as documented

The plan tells the successor to run npm test in seadon.production. That cannot work today, and installing the missing modules is only half the fix.

The repository has no package.json, so nothing records the test dependencies. Four files load jsdom (gift picks, bundle display, cart page, popup flow) and one loads liquidjs from a hardcoded /tmp/lqtest path (hero gate). Run against the checkout as it stands, the suite fails at import: Cannot find module 'jsdom'.

Two of the six run without extra modules today. header-menu-click.test.js passes. popup-signup-flow.test.js fails one assertion: it re-queries the email input after open() replaced that node, so it reads null. That failure is a defect in the test harness, not in the storefront, and it will still be red after the dependencies are installed.

blocked Fix, needs a commit to the theme repository:

cd seadon.production
cat > package.json <<'EOF'
{
  "name": "seadon.production",
  "private": true,
  "scripts": { "test": "node --test tests/*.test.js" },
  "devDependencies": { "jsdom": "^25.0.1", "liquidjs": "^10.16.0" }
}
EOF
npm install
npm test

Then fix the popup harness assertion so the gate can go green, and add node_modules to .gitignore in the same commit. Until the suite passes, the theme publish step in W1 has no automated gate: publish the duplicate, walk the four representative URLs, and record the exception on page 5.

A4 · Deployment procedures

Deploying the app

cd seadon-backer-program
node --test tests/*.test.js          # 288 tests, all green before any deploy
git config user.email logan@seadon.co
vercel deploy --prod --yes            # deploys from the git checkout; alias updates

The identity rule is real: commits must be authored as Logan Solaman <logan@seadon.co> or Vercel blocks the deploy. described A blocked deploy shows as a failed deployment in the Vercel dashboard, and the fix is to amend the author, not to retry.

Before the first deploy under the successor's name, that rule needs a decision: keep logan@seadon.co as the deploy identity, or update the pipeline to accept the successor's address. Pick one, write it down here, and do not leave both.

Publishing the theme

Duplicate, edit the duplicate, preview, test, publish, then sync the files back into git. The full sequence and its rollback are on page 1, W1. Two hard rules: never edit the live theme in place, and remember that a publish is all or nothing across every template.

One script bypasses the editor for targeted uploads: scripts/push-theme-file.mjs sends named repository files to the live theme through the Admin API. It reads SEADON_PROD_ADMIN_TOKEN from ~/.secrets/global.env, is hardcoded to seadonlimited.myshopify.com and Admin API 2025-07, and its usage text still names an older filename. Use it for a single urgent file, not as the normal path: the editor flow is what keeps the live theme and git in step.

A6 · Handling secrets

  • API tokens exist only in Vercel environment variables and in mode-600 .env files on the engineer's workstation. Never in git, never in a document, never in a ticket.
  • A credential pasted into chat, a document or a screenshot counts as compromised. Rotate it rather than deleting the message.
  • Redis connection strings travel with the Vercel project. If the project is transferred, verify them rather than re-pasting them anywhere.
  • The app's /api/health endpoint is deliberately unauthenticated and returns counts only; do not add identifiers to it.
  • No document in this set contains a secret. If you find one, tell Logan and rotate.
