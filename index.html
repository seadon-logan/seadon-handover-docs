What this document set is

Six pages: one orientation page and five by responsibility. They are written to be used at a desk with the Shopify admin open, not read once and filed.

  • Start here is the absolute basics: logging in, the admin map, and a glossary of every term.
  • Page 1 is the day-to-day maintenance manual.
  • Page 2 is the Backer Program operations manual.
  • Page 3 lists what access must move and how the code deploys.
  • Page 4 is the plan for the live sessions with Lisa and Leo.
  • Page 5 is the status board.

The original handover plan (not included in this public copy) remains the reference for function-level detail: the module-by-module reference for both repositories lives in its appendices B1 to B4. This set does not repeat those pages. It tells an operator what to do, in what order, with what to check.

What replaced the video

The plan called for screen-recorded walkthroughs. These pages are the written equivalent: numbered steps with the exact admin path, the button label, a screenshot of the screen, a verification step that proves the change landed, and a rollback line. A screenshot cannot show a hover state or a drag, so steps that need one call it out in words.

How to read the status tags

Each procedure carries one of three tags, because a procedure written from code and a procedure actually run on the live store are not the same evidence.

  • verified Executed end to end on 25 November 2026 and confirmed by reading the result back, usually in a screenshot.
  • described Written from the repository, the handover plan or the admin UI, but the step was not carried out. Treat the first run as a test and expect a small correction.
  • blocked Cannot be completed without a decision or an access change from someone else. The blocker is named.

Claims about numbers or behaviour follow the same discipline inside the text: a figure is either measured here, traced to a named file and line, or labelled as a proposal.

Operating rules that apply everywhere

  1. Never edit the live theme in place. Duplicate it, change the duplicate, preview, run the test suite, publish, keep the old one unpublished as rollback. Page 1, section W1.
  2. A theme publish is all or nothing. Publishing files whose referenced snippets are still in progress breaks the live storefront for everyone.
  3. App tests green before a Vercel deploy, theme tests green before a theme publish. Commands and current state are on page 3.
  4. Commits for the app must be authored as Logan Solaman <logan@seadon.co> or the Vercel deploy is blocked. This is an identity rule in the deploy pipeline, not a preference.
  5. Import with the dry run first. The backer CSV importer writes customer claims and tags; the dry run reports what it would do without writing.
  6. No credentials in documents, repositories or chat. Page 3 says where each credential lives and what to do with it, never the value.

Known gaps in the handover

These are open at the time of writing and are tracked with owners on page 5.

  • The theme test suite cannot run as documented: the repository has no package.json and the tests import jsdom and liquidjs, which are not installed. Page 3 gives the one-line fix.
  • The Backer Program holds a short-lived Admin API token that expires on schedule; the permanent-token swap has not been done.
  • Shopify blocked bulk operations from ASN 12322 until the IP allowlist is filled with the Vercel egress range.
  • assets/seadon-inventory-guard.js is broken past phase 1: it calls functions removed by revert 976a4ae.
  • Someone must be named as the owner of each outstanding item. Where a name is missing, page 5 says so rather than guessing.
  • The campaign rules editor on the storefront admits one email address, and the pages read a GitHub commit pinned by URL, so the rules file has no obvious owner after handover.
